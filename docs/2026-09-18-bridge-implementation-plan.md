# DSH–Obsidian 桥整合实施计划

2026-09-18，用户明确授权按已讨论需求开始施工。此前“等待开工”约束已满足。本计划的各阶段按顺序验收；后续专门笔记、模板、样式和面板操作通道不在本次施工范围。

## 第一阶段：整合已有能力

1. 保留 `dsh-obsidian-bridge-lifecycle` 包名和 `obsidianBridgeLifecycle` 服务名作为升级入口，将独立 Reference Adapter 的宿主与浏览器接入并入桥。桥对外提供连接、消息分派、引用交接及健康信息；Core 保留引用状态、提交、补偿与持久任务。
2. 原 Reference Adapter 成为检测新桥能力的兼容入口；新 Suite 仅加载 Core、Bridge、Sticker 三个运行组件。旧入口与新桥同时存在时不能重复注册来源、消费动作或轮询。
3. 普通贴纸保留笔记关联界面、业务校验和数据。它通过共享通道请求引用和注册已有定位处理器，不再拥有一套桥连接或独立消息轮询。
4. Bridge 自主管理通用连接维护信息。贴纸仍可展示业务同步状态，但不是唯一的桥维护入口。
5. 保留现有 Maintenance 数据归属、会话解析、引用定位和迁移冻结流程。没有可选插件时，独立能力继续运行；已纳管数据不能退回旧副本写入。

验收：动态 Web 端口与已鉴权 Viewer 地址仍来自实际运行实例；选段只投递目标内嵌页面；引用领取幂等、冲突补偿、停止后重连、删除任务、逻辑会话定位保持；普通贴纸本地编辑与关联引用保持；新旧入口并存不重复执行。采用内存存储、合成 HTTP 服务和临时目录，不对真实 Vault／会话执行测试写入。

## 第二阶段：两侧绑定与路由

第一阶段组合验收通过后，才在 DSH Bridge 与 Obsidian Bridge 实施一 Vault 至多一实例、一实例多 Vault。稳定实例身份与每次启动的端口分离。桥拥有有效绑定和路由，维护插件通过桥管理。发现来源先核验现有 Launcher 与宿主身份，再实现自登记及人工配对；Launcher 为可选来源。

同实例 Vault 共用实例勾选的同步工作区范围。取消同步保留历史链接，清楚区分未同步、离线、映射未就绪及会话删除；重新同步后验证原身份再恢复。改绑只影响后续操作，既有引用和排队操作不得改投新实例。

## 第三阶段：维护扩展接入

用户在施工核查中新增授权：Maintenance 自己提供每个 DSH 实例的工作区同步选择，只有选中工作区内容参与实例与真源的双向同步。该能力是有效范围的唯一策略来源；与 Codex 来源导入选择分开。在后续桥绑定完成后，先实现并验收范围存储、设置界面、出站投影与入站回收过滤，再让桥和信息页消费同一结果。撤销范围不能被解释为删除真源，旧运行也不能继续回写已撤销工作区。

在可用的桥绑定接口上，增加 Maintenance 业务扩展注册和插件信息页。数据目录是可复用栏目，插件可提供自身栏目。宿主聚合完整插件名单，避免各插件单独连接时互相覆盖登记；DSH 版本 Adapter 继续只负责宿主会话格式。绑定页和 Adapter 不接管普通贴纸业务。

本阶段验收包含 Maintenance 单独安装、桥系列单独安装和组合安装。有效同步范围必须读取真实实例同步权威来源，不增设另一份勾选名单。

## 分工与交付

- Astra high：Bridge 与旧 Adapter 整合、公共通道及对应测试。
- Astra high：普通贴纸重新接入、维护兼容及对应测试。
- Astra medium：独立核查回归边界、实例身份和同步范围来源。
- 主代理：接口协调、Suite 组装、跨仓组合测试、项目地图与最终验收；前阶段通过后再分派后续阶段。
