## 目标与术语

让一个 Obsidian Vault 始终明确连接到哪个 DSH 实例，并让引用、关联笔记、会话定位和 Session Maintenance 的维护范围保持一致。用户可以只安装其中一组插件；未来的 DSH → Obsidian 操作继续复用同一绑定及路由。

| 术语 | 本文含义 |
| --- | --- |
| Vault／仓库 | Obsidian Vault，不是 Git 仓库。 |
| DSH 实例 | 有独立运行身份与会话存储归属的 DSH 实例，不是一次进程启动或某个端口。 |
| 工作区 | Maintenance 自己的会话分类工作区；不等同于 Vault 或 DSH 按文件夹路径展示的工作区。 |
| 有效绑定 | 当前 Vault 的后续操作采用哪个实例，由 Bridge 负责。 |
| 维护登记 | Maintenance 保存的绑定确认、接入状态和同步回执，反映有效绑定。 |
| 业务 Adapter／贡献方 | 接入 Maintenance 的业务插件及其数据、页面能力，与适配 DSH 会话格式的平台 Adapter 不同。 |
| 历史引用 | 已经保存的实例、工作区、会话、Vault 和引用定位；不会因改绑或取消同步而自动改写。 |

## 已确认需求

### R01：Vault 与实例的绑定关系

- 一个 Vault 至多绑定一个 DSH 实例；尚未绑定是合法状态。
- 一个 DSH 实例可以同时绑定多个 Vault。
- “一 Vault 一实例”的约束由 Bridge 保证，单独安装双侧桥接插件时也必须成立。
- 绑定明确的是稳定实例身份。实例名称、地址或端口变化不等于更换实例。
- 多个 Vault 的同名笔记、相同相对路径及各自的连接必须可区分；关闭一个 Vault 不应使同实例的其他 Vault 断开。

### R02：两个管理入口共用有效绑定

Obsidian 侧插件设置页提供当前 Vault 的实例选择、绑定状态和改绑入口。Session Maintenance 在“扩展数据”中的对应业务信息页提供实例视角的集中管理，展示与这个实例关联的 Vault。

两个入口使用同一绑定能力。Bridge 负责确认有效关系；Maintenance 负责管理展示、维护登记和回执。不能让两个入口分别保存可独立生效的绑定，造成设置页显示实例 A、维护页却认为实例 B 的情况。

### R03：本机发现与动态端口自动连接

实例发现要服务于绑定选择，同时保持 Bridge 的独立运行能力。Launcher 可以提供有用的实例信息，但不成为基础绑定与连接的必需依赖。

Launcher 每次启动实例可能分配不同 DSH Web 端口。已经绑定的 Vault 应在同一实例重启、端口改变和登录地址更新后自动续接，不能要求用户每次重新选择实例或填写端口。其他实例后来启动，或占用原端口，也不能改变这个 Vault 的有效归属。

首次配对与以后自动重连是两个过程。配对确定长期目标，重连更新该目标的当前运行位置。本机登记的具体位置和发现协议仍属于工程设计，见后文。

### R04：业务扩展信息页与栏目

Session Maintenance 对其他插件公开业务扩展注册能力。每个业务 Adapter／贡献方可以登记并维护自己的信息页与栏目，不要求 Maintenance 针对每个插件写死页面。

“数据目录”只是信息页中的一个可复用栏目。其他栏目可以包括绑定关系、连接状态、同步情况、维护回执，以及插件需要的业务内容。页面应允许标准栏目和插件提供的定制内容。

Obsidian 的绑定管理放在相应业务页中；其栏目由实际提供相关能力的插件贡献。组合展示不改变各插件的数据和操作责任。平台 Adapter 继续处理宿主会话格式，业务扩展注册不由它承担。

### R05：所有 Vault 共用实例的同步范围

不同 DSH 实例可以选择同步不同工作区。绑定同一个实例的所有 Vault 共用该实例已经勾选的全部同步工作区，不再增加每个 Vault 单独缩小范围的名单。

例如：实例 A 同步工作区甲、乙，绑定它的 Vault 1 和 Vault 2 都使用甲、乙；实例 B 只同步丙，绑定 B 的 Vault 3 使用丙。Vault 不会因为另一个实例同步了某工作区，就自动获得那个实例的会话。

工作区同步策略有自己的权威来源，Bridge 消费其有效结果，不保存另一份竞争策略。此规则针对接入维护能力的模式；没有 Maintenance 时，基础插件按自身原生能力运行，不能把“未安装维护能力”显示成“这个工作区被用户取消同步”。

### R06：取消同步、恢复同步与删除的区别

2026-09-18 施工核查时补充确认：当时源码尚未提供 DSH 目标实例的工作区选择，用户授权在 Maintenance 新增此功能。它成为 R05 所述范围的权威来源；只有被选中的工作区内容才参与该 DSH 实例与真源的双向同步。现有 Codex 来源导入的勾选仍是独立策略，不能拿来替代，也不由 Bridge 再保存另一份名单。

用户进一步确认：这里的工作区是 Maintenance 自己的会话分类工作区，区别于 DSH 按文件夹路径展示的工作区。未分类会话单独选择；未配置实例默认全部同步，明确空选择表示不再同步任何会话。保存后的范围在实例下次启动时生效，页面分别显示已保存范围和当前运行范围；当前运行按原范围完整保存。

一个工作区从当前实例取消同步、且新范围在下一次启动生效后：

- Vault 中已有的链接和引用继续保留，原实例、工作区、会话、Vault 及引用身份不变。
- 点击相关旧链接时显示“当前绑定实例未同步此工作区”。
- 与该工作区有关的新增关联、引用投递和需要访问会话的同步操作暂停。
- 不自动删除链接，不自动改绑，不自动切换到另一个实例。

重新勾选后，核验原逻辑会话到当前实例的映射，再恢复相关操作；不要求重新创建引用。真正删除的会话显示“会话已删除”，离线、未同步和映射尚未就绪分别表达。单次查询失败或列表中没有出现会话，不等于会话被删除。

### R07：改绑不重写历史

改绑改变的是后续操作的目标。旧引用继续记录原来的实例、工作区、逻辑会话、Vault 和引用身份；历史数据迁移不是改绑的隐含动作。

改绑前尚未完成的请求保留原目标，不能在改绑后自动发给新实例。历史目标暂不可访问时明确显示原因。解除绑定也不应被解释为删除所有历史引用。

### R08：两组插件可以分别正常运行

| 安装／运行情况 | 期望行为 |
| --- | --- |
| 只装 Session Maintenance | 会话维护和已安装业务扩展正常运行，不因缺少 Obsidian 系列报启动错误。 |
| 只装 Obsidian–DSH 系列 | Bridge 绑定、连接、基础引用与导航正常；不要求安装 Maintenance。 |
| 两组都装 | 可选接入维护登记、逻辑会话解析、同步范围和业务管理页。 |
| 可选插件未安装或被禁用 | 将能力缺席视为正常状态，不启动持续失败的请求循环。 |
| 已接入的维护能力暂时离线 | 保留历史数据和未完成状态，按可恢复故障处理，不伪装为未安装或空数据。 |

独立运行不要求复制对方的全部功能。需要 Maintenance 的维护操作可以明确显示不可用，基础插件仍应正常启动并使用其独立能力。已经托管的数据在维护能力消失后，不能悄悄恢复对旧副本的写入；退出托管如有需要，另行设计明确的交还过程。

### R09：为 DSH → Obsidian 专门操作通道保留扩展能力

后续希望让 DSH／LLM 通过专门通道操作已绑定的 Obsidian，例如写入或修改笔记，再扩展笔记模板、样式、面板以及 Obsidian 插件注册等能力。

读写应由 Obsidian 一侧的能力执行，DSH 发出有明确目标与结果的操作请求，避免让 LLM 为这些业务自己拼系统文件操作命令。这里不意味着底层不再进行文件读写。

现阶段要求保留可扩展性，复用实例／Vault 绑定和路由，并能辨认目标 Vault 支持哪些操作。本轮不实现上述未来业务。用户已确认其通道归同一个 DSH Bridge 插件，并与 Obsidian Companion 内部执行能力协作，不再另设用户需要管理的桥接插件；具体业务能力仍另行设计。

用户进一步确认：纯笔记操作不必经过 Core 的引用流程，也不必经过 Maintenance。专门操作通道留到桥整合、绑定与路由、维护接入完成之后再展开，不加入第一阶段重构。

### R10：普通贴纸保留笔记关联，桥提供共用双向引用通道

笔记关联是普通贴纸的业务功能，面板、关联规则和业务操作继续归 Sticker Board。撤回把笔记关联功能迁入 Bridge 的建议。

整合后的 DSH Bridge 与 Obsidian Bridge 对外提供共用双向引用通道；普通贴纸自行适配这个通道。其他跨 DSH／Obsidian 的业务在需要引用时也使用相同通道，不各自建立连接、领取、回链和删除同步流程。Core 继续拥有通用引用状态、提交和补偿，桥负责跨宿主的交接，贴纸负责业务意图及自身对象。

用户确认第一阶段只整合已经存在的引用、回链、定位和解除能力，保留后续扩展接口，不新增双向交互业务。此处“双向引用通道”与未来任意笔记／样式／面板操作通道分开排期。

### R11：先重构，再开发绑定与路由，最后接入新的维护能力

用户确认推进顺序：

1. 整合 DSH 侧桥接插件与已有功能，普通贴纸重新适配共用通道，完成现有行为的回归验收。
2. 在整合好的 DSH Bridge 与 Obsidian Bridge 中实现 Vault／实例绑定与 Vault 路由，包括实例发现、动态地址续接和多 Vault 隔离。
3. 在桥能力完成后，新增 Session Maintenance 的业务 Adapter 接入、扩展信息页、绑定登记和维护范围协作。
4. 前述工作完成后，再展开专门操作通道。

第一阶段必须保留当前已接入 Maintenance 的贴纸、引用和会话定位能力。第三阶段后置的是新的公开扩展页和绑定 Adapter，不能据此先断开已有接入或让已托管数据恢复旧副本写入。

Vault 路由由两侧 Bridge 承担，Maintenance 接入消费桥能力，不持有另一套有效绑定或路由实现。第一阶段可整理清楚目标上下文与接口位置，完整多 Vault 行为在第二阶段实现。

### R12：桥接层合为一个用户安装插件

用户在交付核查中明确纠正：只合并内部实现、继续保留 Suite 父组和多个桥包的交付形态不够。当前 DSH 桥产品统一为 `dsh-obsidian-bridge@0.4.1-rc2.1`，实例/Vault 绑定、路由、共享双向引用、桥维护和未来专用通道都归该插件。

- Core、普通 Sticker 和 Session Maintenance 保持独立，职责不因桥打包收敛而迁移。
- Suite 仓库只保留私有开发、文档与组合验收，不再提供可安装 wrapper 或运行父组。
- Profile 独立加载 Core、Bridge、Sticker 各一次，依靠 Cordis 服务处理可选能力、晚加载和卸载，不依赖固定父组顺序。
- 旧 Lifecycle 物理 Git 目录和内部 `obsidianBridgeLifecycle` 服务名可保留兼容；用户只管理新的 Bridge 安装项。
- 旧 Reference Adapter 退役，不列候选安装成员；Protocol 是内部开发库，不由用户单独安装或启用。
- Obsidian Companion 仍是另一宿主的插件，不因 DSH 侧收敛而取消。真实安装与窗口验收须检查新的产品形态。

### R13：业务组合与 Core 运行时引用职责

用户进一步明确：普通 Sticker 同时依赖 Bridge、Core 和 Better Sidebar；Core + Bridge 直接实现跨 Obsidian 引用；Core + ThoughtDAG 直接实现跨会话引用和会话贴纸。会话贴纸不归普通 Sticker，通用引用也不整体移进 Bridge。

Core 自己负责运行时引用状态、上下文组织与注入、引用样式与 UI、气泡，以及提交、撤销和恢复。Bridge 管 Obsidian 来源、传输、定位、实例/Vault 绑定；ThoughtDAG 管会话来源关系；普通 Sticker 调用 Core 并保留自身业务。

Maintenance 独立可选，通过各业务 Adapter 保存恢复相应的历史消息与业务类型，不接管 Core 的运行时引用。业务依赖缺失时显示不可用或等待，服务晚加载后可接入，不以启动报错替代能力状态；已托管数据不回退旧副本写入。

## 典型使用流程

1. 打开一个未绑定的 Vault，在 Obsidian 设置页查找或配对本机 DSH 实例，选择实例 A。
2. Bridge 确认绑定后，Vault 的后续引用、导航及未来操作采用 A；有 Maintenance 时，其对应业务页也显示这个绑定。
3. 第二个 Vault 同样可以绑定 A。二者分别路由到自身笔记，同时共用 A 的工作区同步范围。
4. Launcher 重启 A 并换了端口，连接自动更新，两个 Vault 的绑定保持。
5. 用户从 A 取消工作区甲的同步，两个 Vault 对甲的旧链接都保留并显示未同步；恢复勾选后核验原映射再恢复。
6. 若把第一个 Vault 明确改绑到 B，新的操作采用 B。旧引用仍保留 A 的历史身份，第二个 Vault 继续使用 A。

## 当前职责基线与改动范围

当前基线继续是：Core 提供通用引用机制和原生主会话划选；ThoughtDAG 拥有跨会话业务入口及会话贴纸；Sticker Board 保留普通贴纸、迁移及 Obsidian 双向链接。依据见 [已有职责决定](project/records/decision/selection-ownership-20260918.md)。新增确认只收敛桥接公共能力，贴纸的笔记关联继续由贴纸拥有；顺序与通道分工见 [桥整合与分期决定](project/records/decision/bridge-refactor-sequence-20260918.md)。

## 工程方案及尚待核查的实现细节

下面记录此前提出的工程方案，便于接续实现；它们不是用户逐字段确认的产品要求。

- 本机发现优先采用 Bridge 自登记，手动配对兜底，Launcher 目录作为可选补充；不依赖全盘扫描或猜测端口。
- 分开保存稳定实例／Vault 身份、有效绑定与当前运行端点；使用运行代次、绑定修订与确认结果处理重启、并发改绑和旧响应。
- 有效绑定的写入在 Bridge 侧收敛，维护页收到确认后再更新生效登记；具体持久化位置由 Bridge 设计约束。
- 公开贡献注册由宿主汇总参与者，各插件只维护自己的贡献；不能让一个插件的小名单清掉其他插件。
- 标准栏目与定制页面遵守宿主、Engine、管理界面的实际进程分工；跨进程不直接传函数。
- 实施前核对真实稳定实例 ID 的传入方式、每实例有效同步范围的权威来源、登记目录与协议版本、旧配置迁移和页面资源装载。

提供方接口草案分别见 [Bridge 设计](2026-09-18-vault-instance-binding-design.md) 与 [Maintenance 设计](../../dsh-session-maintenance/docs/superpowers/specs/2026-09-18-extension-pages-and-instance-scope.md)。本稿统一产品要求，接口合同仍由提供方维护。

## 后续验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同实例绑定两个 Vault，存在同名笔记 | 引用与操作分别到正确 Vault，单个 Vault 关闭不影响另一个。 |
| 两处管理页同时改绑 | 只有一个有效结果，双方最终一致，未确认不显示完成。 |
| 同实例换端口、换登录地址，旧端口被另一实例使用 | 自动恢复正确实例，绑定和历史身份不变。 |
| 同实例多个 Vault，工作区取消同步／恢复同步 | 范围一致、旧链接保留、提示正确，恢复时核验原映射。 |
| 操作列表已经打开，随后保存新的范围 | 当前运行继续使用原快照；下次启动使用新范围，提交时核验该运行有效范围及当前会话归属。 |
| 改绑时存在历史引用与待处理请求 | 原归属保留，旧请求不转投新实例。 |
| 分别安装、先后启用、禁用再启用、暂时离线 | 基础功能正常，能力缺席无失败循环，已托管数据无双写。 |
| 多个插件注册栏目，其中一个卸载或失败 | 其余栏目继续工作，其他插件登记与持久数据保留。 |
| 合成操作能力注册、调用、注销 | 按 Vault 识别能力和返回结果，未安装的操作显示不可用。 |

上表定义产品验收条件。当前已完成的合成场景、构建及回归见交付记录；未来通用操作能力的注册/调用场景仍后置。合成测试不等于真实实例与用户 Vault 的完整运行验收。

第一阶段单独按已有行为验收：引用接收、回链、定位、解除、普通贴纸与笔记关联、当前动态端口连接，以及现有 Maintenance 集成继续可用；卸载 Sticker 不影响基础桥管理。多 Vault 独占绑定和新的扩展页属于后续阶段，不能用它们代替第一阶段的回归结果。

## 首版范围之外

跨机器发现、跨实例自动重路由、历史数据自动迁移、Vault 私有工作区名单，以及未来笔记／模板／样式／面板／插件操作的具体实现不属于第一阶段重构。后续阶段按 R11 推进，不合并成一次施工。
